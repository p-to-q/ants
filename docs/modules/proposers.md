# proposers

Baseline arms and the LLM proposer: random, evo (tournament + credit-weighted mutation), tpe (Optuna), llm.

**Interface**
- `make_proposer(arm, c, seed, client, memory_fn, llm_share)`; arms: `random`, `evo`, `evo_percap`, `qd`, `tpe`, `portfolio`, `portfolio_lean`, `portfolio_screen`, `portfolio_llm`, `portfolio_dream`, `portfolio_agent`, `llm`, `llm_dream`, `agent`. The arms that already have ledgers (`portfolio`, `portfolio_llm`, `portfolio_agent`, `portfolio_dream`) are pinned to the behaviour they had in 0.6.0 (`LEGACY_PORTFOLIO`; `tests/test_screen.py` asserts the definition hash the server recorded and the sequence of proposals); a new design is a new arm name. Every proposer returns `Proposal(spec, source, note, origin_key, edit)` so lineage is recorded.
- `rank_specs(ledger, c, arm, epoch=None)`: one row per spec at its deepest stage; with `epoch`, only evidence from that epoch. `Campaign.frontier` and `freeze_best` pass the campaign's epoch.

**Invariants**
- Every proposal is validated against the Space; LLM proposals also pass a novelty filter (exact and near-duplicate rejection).
- `LLMProposer` fills a buffer in background threads so slow calls overlap with CPU evaluation; empty buffer falls back to evo. `inflight` is released in a `finally`, so a malformed reply is counted as a failed call and cannot stall the LLM arm. Hints written by `ants hint` are stored as one cleaned line; the prompt reads the latest three `user_hint` events as they are in the ledger.
- Memory text from `dream` and hints are data inside the prompt; the reply is still only accepted through `Space.validate`.

**Notes / failure behaviour:** Unparseable or invalid LLM output is counted, not repaired. The plain `tpe` arm reads all `done` trials of the arm (every epoch) from the ledger, and the LLM proposers build their prompt history without an epoch filter; the other arms use the campaign's epoch-filtered `History` when it is passed in. `optuna` is needed only for `tpe` arms and is skipped by the portfolio when missing.

**The learned screen** (`screen.py`, arm `portfolio_screen`; roadmap step 43). Between the first and the second stage the contract's quantile rule is replaced by a model fitted on the arm's own finished second-stage trials: extremely randomised trees (numpy, 60 trees, refitted every 100 new results, a fit takes about a second) on the specification and the first-stage metrics, predicting the second-stage value with the spread of the trees as uncertainty. A first-stage result is promoted when its optimistic score (mean minus 0.5 spread) is within the best share of the last 400 candidates of its size cap, where the share is chosen so that, together with a uniformly random 10% of the rest, the same fraction is promoted as under the quantile rule (the workload does not change). The random share is a pure function of seed and trial id. Until 150 second-stage results exist, and whenever a fit fails, the quantile rule decides. Every decision is a `screen_decision` event with its mode, the prediction, the cut and the exact probability of promotion (1 for a model decision, the random share otherwise), which is what a later off-policy estimate needs. The settings are part of the arm definition; the arm definition of every other arm is unchanged.

**Operator allocation log.** Each allocation of the portfolio's bandit writes an `operator_alloc` event: the probability each operator had, the number drawn, the burst, and a tag for the version of the rule. It does not change what is proposed (the proposal sequence is identical to the unlogged one).
